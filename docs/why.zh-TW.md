# 為什麼需要這個專案

我從國中就開始動手做東西 —— 最早是 Arduino 草稿碼，現在是 PCB 與交易系統。AI 是我的工具箱，也是我學習循環的一部分：我用 Opus 4.6 思考（天生的規劃者兼辯論者），用 Sonnet 5 + Opus 4.8 執行（嚴格的提示詞遵循者，生來就是要交付成果），並在任何東西上線前，用 Gemini、Copilot 與 Codex 交叉檢查。

每個模型都有與其訓練方式契合的任務：

- **思考** —— claude.ai 上的 Opus 4.6 保留我的個人記憶、與我辯論各種方案，並在我投入之前先對計畫做壓力測試。它的訓練偏重推理，也擅長拿捏細微差異 —— 規劃正需要這些。
- **執行** —— Sonnet 5 撰寫程式碼；Opus 4.8 當顧問幫我看。兩者都受過嚴格遵循提示詞與精確輸出的訓練 —— 它們負責交付成果，不空談哲學。
- **交叉檢查** —— `consult` 把同一個 prompt 同時送給 Copilot、Codex 與 Gemini。不同的訓練資料、不同的盲點、各自獨立的判斷。沒有任何單一模型能說了算。
- **迭代** —— 所有結果最後都回到我手上。由我整合、定奪，再開下一個循環。每一道關卡都還是由我決定（human-in-the-loop）。

除了模型選擇之外，每次委派都會附帶一個**角色提示詞（role prompt）** ——「身為資安稽核員…」、「身為前端工程師…」、「身為 Karpathy 風格的程式碼審查員…」—— 讓模型從特定專業的角度回答，不要當泛用的助手。我維護著一份完整的角色表（涵蓋工程、產品、內容與研究等 20 多個角色），把每個角色對應到合適的模型層級與工具。

這些 bridge 就是把交叉檢查變成程式呼叫的管線，不必在各個聊天視窗之間手動複製貼上。
